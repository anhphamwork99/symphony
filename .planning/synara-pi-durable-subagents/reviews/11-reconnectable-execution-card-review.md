## 3. Findings

### R1 — BLOCKING: bridge publishes card events only for the NEWEST execution of a thread

**Location:** `apps/server/src/provider/piSubagentExecutionCardBridge.ts:77-83`

```ts
const cards =
  yield *
  repository.listExecutionCardsByThreadId(
    notification.parentThreadId,
    1, // ← thread-scoped list, newest-first, LIMIT 1
  );
const match = cards.find((card) => card.executionId === notification.executionId);
```

`listExecutionCardsByThreadId(threadId, limit)` selects the thread's rows `ORDER BY created_at DESC, execution_id DESC LIMIT n` (Repository.ts:636-641). With `limit=1` it returns ONLY the newest-created execution of the thread. Any lifecycle-truth commit (lifecycle event, cancel intent/ack, terminal, orphan) on a NON-newest execution — a first-spawned worker that finishes or is cancelled while a later sibling exists — yields `match === undefined`, and the bridge silently publishes nothing. The comment at `:73-75` ("The thread query is capped at the card window; a cap-evicted execution means … nothing to project") conflates "cap-evicted (64+)" with "not the single newest"; evictions were the intended boundary, not sibling masking.

**Consequence:** for multi-execution threads (explicitly supported — T22-AC6 concurrent executions; the ticket's own AC6 test admits siblings), AC2's live lifecycle publication and AC6's "visibly cancelling until acknowledgement" never reach the client for all but the newest execution. The event is not merely dropped in transit — it is never CREATED, so reconnect replay cannot recover it either; only a fresh full snapshot resync shows the new truth. This is a material failure of the ticket's core promise.

**Reproduction (performed in the clean worktree, scratch test since deleted):** real engine + real repository, thread with `exec-old` (created 00:00:01) then `exec-new` (00:00:02); `recordLifecycleEvent(running, seq 2)` on `exec-old`. Result: `card events: exec-old,exec-new` (admissions only) and ZERO events carrying `observedState:"running"` for `exec-old` — assertion `expect(oldRunning.length).toBeGreaterThan(0)` failed with `expected 0 to be greater than 0`.

**Why the shipped tests missed it:** `piSubagentExecutionCardSurface.test.ts` uses exactly one execution per thread in every publication test; the multi-execution case exists only in the coordinator test, which bypasses the bridge.

**Disposition (recommended):** read the card by execution identity (e.g., `getById` + observation/terminal/outbox join, or extend `listExecutionCardsByThreadId` with an execution-id filter, or a dedicated `getExecutionCard(executionId)` repository seam), keeping the cap-eviction early-return as the only skip condition. Add a regression test: two executions in one thread, lifecycle event on the older one must publish that execution's card event; also assert the cap-eviction case still skips.

### R2 — LOW: no end-to-end test of the card-cancel wiring (decider → reactor → ProviderService → PiAdapter)

**Location:** `apps/server/src/orchestration/decider.ts:1853-1876` (cancel case), `apps/server/src/orchestration/Layers/ProviderCommandReactor.ts:2851-2876, 3650-3653` (reactor case).

The dispatch chain for `thread.pi-subagent-execution.cancel` is proven only piecewise: coordinator unit tests (real repository, fake bridge), ProviderService shape registration in the reactor harness mock (`ProviderCommandReactor.test.ts:378,516,690` — mock registered, never driven by a cancel event), decider case untested (shares `requireThread` with `thread.task.stop`), adapter method untested through the service routing (`allowRecovery:false`, `routed.isActive`, capability gate). tsc + full suites pass, and the sibling `thread.task.stop` pattern is long-established, so wiring risk is low — but Decision 0001 requires failure/diagnostic coverage at the responsible boundary, and today no test dispatches this command against a real engine and observes the journal intent. **Disposition:** add one engine-level test dispatching `thread.pi-subagent-execution.cancel` (existing engine harness pattern, as `piSubagentExecutionCardSurface.test.ts` builds one) asserting the journal `cancelling` intent and the denial activity for an inactive session.

### R3 — LOW: the legacy "Unmanaged (legacy)" label is unreachable in the live UI

**Location:** `apps/web/src/components/ChatView.tsx:11327` (`piSubagentExecutionCards.length > 0 && !planSidebarOpen` gate) vs `ChatView.tsx:2921-2924` (`piSubagentLegacyAgentToolActive` requires `piSubagentExecutionCards.length === 0`).

The strip — the only consumer of `legacyAgentToolActive` — mounts only when at least one managed card exists, but the flag is true only when zero cards exist. The label is therefore dead code in production; a legacy session running the Agent tool shows nothing (the AC8 "labeled unmanaged/non-durable in the execution-card experience" half is unmet end-to-end), while the component test passes in isolation. Note the display heuristic itself (Pi provider + running latest turn + zero cards) would also mislabel a managed session whose executions are all cap-evicted, so the fix should consider the negotiated-capability signal rather than inferring from absence. **Disposition:** mount the strip when `piSubagentExecutionCards.length > 0 || piSubagentLegacyAgentToolActive`, or render the legacy label through a dedicated lightweight row outside the cards gate; align the heuristic with session capability truth.

### R4 — INFO: outbox delivery-state transitions never publish card updates

`markCompletionDelivered` / `markCompletionAcknowledged` / `markCompletionDeliveryFailed` / `markCompletionSuperseded` return `{kind:"transitioned", entry}` (no `execution` field), so `notifyIfLifecycleTruthChanged` never fires for them (Repository.ts:3236-3249). The card exposes `deliveryState`, so a live client can show a stale `pending` badge until the next lifecycle event or snapshot. Snapshot/reconnect reads current truth, so this is a freshness lag, not a correctness break, and AC1/AC2 as written are satisfied. Note that once R1's by-execution read exists, wiring a notification for delivery transitions would be a one-line extension if the owner wants live delivery badges.
